# task_sync_app

日本語で書いたタスクの行から、**期限**と**カテゴリ**を自動で取り出すアプリです。
スマホのホーム画面に追加して使える PWA（ウェブアプリ）と、解析を行う API（FastAPI）でできています。

## できること
- タスクを1行ずつ貼り付けると、行ごとに「題名・期限・カテゴリ」と、期限をどう読んだか・要確認の印を表示します。
- カテゴリは、設定（JSON）に書いた判定語で分けます。どの語で決めたか（判定の理由）も表示します。
  公開しているのは見本の設定（仕事・学び・地域・暮らし）だけです。実際に使うカテゴリは、環境変数などで渡します（下の「カテゴリの設定」）。
- 解析したタスクを、**この端末の中**（ブラウザの IndexedDB）に保存できます。サーバーには保存しません（下の「端末に保存したタスク」）。
- 期限のあるタスクを、カレンダー用ファイル（.ics）にして保存できます。カレンダーのアプリで読み込みます（下の「カレンダー用ファイル（.ics）」）。

## 端末に保存したタスク（本人の番）
保存の方針（なぜ端末の中か・Render の無料枠との比較）は [docs/storage.md](docs/storage.md) にあります。

- 「解析」で解析したあと「端末に保存」を押すと、この端末の中に保存します。各タスクには、最初に**固定の ID（UUID）**を振ります。
- 「一覧」タブで、状態（進行中・本人の番・完了・保留）・レーン・「次に本人がすること」を変えられます。
- 「本人の番」タブ（携帯で見る画面）には、状態が本人の番のタスクだけが出ます。
  最後に動いてから **48 時間以上**たったものには「2日以上動きなし」の印が付き、先頭に並びます（完了・保留には付けません）。
- **端末の引っ越し・控え**: 「JSON に書き出す」でファイルにし、もう一方の端末の「書き出した JSON を読み込む」で入れます。
  同じ ID のタスクは、更新の新しい方を残します。自動の同期はしません。
- **Notion の台帳へ**: 「台帳の形でコピー」で、件名・レーン・状態・本人の番・更新日 の Markdown の表か CSV をクリップボードに入れます。
  「本人の番」の列には「次に本人がすること」が入ります。クリップボードが使えないとき（http で開いたときなど）は、選んでコピーする欄に出します。
- **Notion の台帳から**: 「本人の番」タブで、Notion から書き出した CSV を選ぶと、状態が「本人の番」の行だけを表示します（保存はしません）。
  1行目に「件名」と「状態」の列が要ります。更新日が2日以上前なら印を付けます。Notion の書き出しの日付の形は未確認です。
- レーン名は「一覧」の「レーン名の設定」で変えられます（この端末だけ）。公開しているコードには見本の名前（仕事・学び・暮らし）だけを置いています。
- **外部には送りません。** 保存・書き出し・コピーはブラウザの中だけで行います（テスト `tests/test_b29_no_network.py` で、通信の書き方が増えていないことを確かめます）。
- ブラウザの「サイトのデータを消す」や、Safari でこのサイトを 7 日間（Safari を使った日で数えて）操作しないことなどで消えることがあります。ときどき JSON に書き出して控えを取ってください。
- 計算（状態・印・台帳の形・CSV・JSON）は `frontend/task_core.js`、保存場所は `frontend/store.js` です。

## カレンダー用ファイル（.ics）
- 「解析」の結果の「**カレンダー用ファイルを保存**」で、期限のあるタスクを .ics ファイルにします。
  先に端末に保存して固定の ID を振り、その ID を予定の UID（予定を見分ける番号）にします。
  「一覧」の同じボタンでは、期限のある未完了のタスクをまとめて書き出します。期限の無いもの・完了は入れません。
- 予定は**終日**です（期限の日だけ。時刻は説明欄に書きます）。RFC 5545（.ics の決まり）に沿って、1行 75 オクテットで折り返し、改行は CRLF にします。
- UID は題名や期限を直しても変わりません。読み込み直したとき、同じ UID の予定を上書きするか、別に足すかは**カレンダーのアプリ次第**です。
  Google カレンダーは上書きするという二次情報（例: https://addcal.co/blog/how-to-add-an-ics-file-to-google-calendar 、検索の抜粋で確認・2026-10-01）がありますが、公式の説明はこの環境から開けず**未確認**です。iPhone・Windows の実機でも未確認です。
- 外部への送信も、OAuth（Google のログイン）も、鍵もありません。ファイルはブラウザの中で作ります。
- `POST /api/sync-calendar` は使いません（501 を返します）。作るのは `frontend/ics.js`、検算は `tests/frontend/ics.test.mjs` と `tests/test_b30_ics.py`（icalendar で読めることを確かめます）です。

### 前のカレンダー同期（`backend/task_sync/calendar_client.py`）を使わない理由
- **手元の PC 向けの認証です。** `credentials.json` と `token.json` をファイルで持ち、その PC でブラウザを開いて許可する形（`InstalledAppFlow`）なので、Render のサーバーでは動きません。
- **権限が広すぎます。** `https://www.googleapis.com/auth/calendar` を求めます。Google の説明では「See, edit, share, and permanently delete all the calendars you can access using Google Calendar」（見られるすべてのカレンダーの閲覧・編集・共有・完全な削除）です。期限の目印を足すだけには要りません（出典: google-api-python-client に入っている Calendar API の説明 `discovery_cache/documents/calendar.v3.json`、revision 20260708。2026-10-01 に確認）。
- **予定が二重に登録されます。** 重なりを防ぐ `task_id` は「カテゴリ・題名・期限日」のハッシュ（sha256 の先頭 16 文字）です。
  期限や題名を直すと別の値になり、前の予定を見つけられずに新しい予定を足します（前の予定は残ります）。カテゴリの判定が変わったときも同じです。
  探す範囲も「今日の 30 日前〜180 日後」だけなので、その外の予定も見つけられません。逆に、カテゴリ・題名・期限日が同じ別のタスクは同じ値になり、1つにまとまってしまいます。
  （期限や題名を変えると `task_id` が変わることは `tests/test_b30_ics.py` で記録しています）
- .ics の UID は最初に振った固定の ID（UUID）なので、この問題がありません。

**ファイルの扱い（決めたこと）**: `calendar_client.py`・`sync.py` は、削除も docs/ への移動もせず、今の場所に残します。Web アプリ（`backend/api.py`）からは使いません。
- 理由: 手元の PC で試すときの部品として動く形のまま残せること、テスト（`tests/test_task_sync.py`）があること、依存（`requirements-calendar.txt`）は本番に入れていないこと。削除は git の履歴から戻せますが、作者のコードなので、消すかどうかは作者が決めるのがよいと考えました。
- 消すときは、`backend/task_sync/sync.py`・`requirements-calendar.*`・CI（`.github/workflows/ci.yml`）の依存・`.claude/hooks/session-start.sh`・`tests/test_task_sync.py` の該当テスト・この節を一緒に直します。

## カテゴリの設定
カテゴリの名前と判定語は、コードに書かず、設定（JSON）から読みます。判定の正本は `backend/task_sync/categories.py` で、
画面・API と、カレンダー同期用の `backend/task_sync/parser.py` が同じ判定を使います。

### 読み先（上から順に、最初に見つかったもの）
1. 環境変数 `CATEGORY_CONFIG_JSON` … 設定の JSON そのもの（**Render ではここに貼ります**）
2. 環境変数 `CATEGORY_CONFIG_FILE` … 設定の JSON ファイルの場所
3. `private/categories.json` … 手元だけのファイル（`private/` は .gitignore 済み。コミットされません）
4. `backend/task_sync/categories.sample.json` … 公開している見本（仕事・学び・地域・暮らし）

読めない設定（JSON の書き間違いなど）は使わず、見本に戻します。理由はログと `/api/health` の `category_config.error` に出ます（設定の中身は出しません）。
今どの設定を使っているかは、`/api/health` の `category_config.source`（`env`・`file`・`local`・`sample`）で分かります。

### 設定の形
```json
{
  "version": 1,
  "default": "暮らし",
  "exclude": ["国会議"],
  "categories": [
    {"name": "仕事", "color": 1, "keywords": ["会議", "資料", "議事録"]},
    {"name": "地域", "color": 2, "keywords": ["町内会", "総会"], "aliases": ["町会"], "exclude": ["株主総会"]},
    {"name": "暮らし", "color": 4, "keywords": ["買い物", "病院"]}
  ]
}
```
| 項目 | 意味 |
|------|------|
| `categories` | カテゴリの一覧（12 個まで）。**書いた順が、同点のときの順**です |
| `name` | カテゴリ名（30 文字まで）。文の中に名前そのものがあれば、それも1点です |
| `aliases` | 名前のほかの書き方（かな・略称など）。名前と同じ扱いです |
| `keywords` | 判定語。文の中にあれば1点です |
| `color` | 画面の印の色の番号（1〜6）。色そのものは画面の CSS（`.badge-cat-1`〜`6`）で決めています |
| `exclude`（全体） | 除外語。この語の中に出てきた判定語は数えません（例: 「国会議員」の中の「会議」） |
| `exclude`（カテゴリ） | この語が文にあれば、判定語ではそのカテゴリにしません。名前（`name`・`aliases`）が書いてあれば、そのカテゴリにできます |
| `default` | どの語にも当たらないときのカテゴリ（`categories` の中の名前） |
| `_` で始まる項目 | メモとして読み飛ばします（例: `"_note"`） |

### 決め方
- 当たった語の数がいちばん多いカテゴリにします。同点なら、設定で前に書いたカテゴリです。どれにも当たらなければ `default` です。
- 文字は全角・半角と大文字・小文字の違いをそろえてから比べます。
- **語の境界**: 1文字の語は、すぐ後ろに同じ種類の文字（漢字・ひらがな・カタカナ・英数字）が続くときは数えません
  （例: 判定語「本」は「本田さん」では数えません。「本を読む」「古本」は数えます）。英数字だけの語は、前後が英数字なら数えません。
- 同じ場所で、長い語の中に入っている短い語は数えません（「役員会」と「役員」が両方とも判定語でも、「役員会」は1点）。
- 判定の理由として、当たった語（`category_hits`）を返し、画面に「カテゴリの理由: 「会議」「資料」」と出します。

### Render で実物の設定を使う
公開しているリポジトリには見本しか置きません。実際のカテゴリは、Render の環境変数で渡します。
1. 手元で設定ファイルを作り、確かめます（`private/` の下に置けばコミットされません）。
   ```bash
   python scripts/category_config.py check private/categories.json      # 形を確かめる（数だけを出す）
   python scripts/category_config.py try private/categories.json "会議の議事録"   # 判定を試す
   python scripts/category_config.py env private/categories.json        # 1行の JSON を出す
   ```
2. Render のダッシュボードで、このサービスの **Environment**（環境変数）を開き、キー `CATEGORY_CONFIG_JSON`、値に 1. の `env` で出した1行を貼って保存し、デプロイし直します（アプリは起動のときに設定を読みます）。
3. 開いて、`/api/health` の `category_config` が `{"source": "env", "categories": （数）, "error": null}` になっていることを確かめます。
   画面で1行解析し、カテゴリの印と「カテゴリの理由」を確かめます。

**注意**: 環境変数を設定しないまま、この変更を main に入れると、公開中のアプリのカテゴリが**見本（仕事・学び・地域・暮らし）に変わります**。
先に環境変数を設定してから main に入れてください。端末に保存したタスク（IndexedDB）のカテゴリ名は、保存したときのまま変わりません。
Render の画面の名前は変わることがあります（この説明を書いた環境からは Render の公式の説明を開けず、未確認です）。

### 公開したくない語が残っていないかを確かめる（手元）
実名・団体名・私用メールのドメイン・手元のパスなどを1行1語で `private/words.txt` に書き（コミットしない）、次を実行します。
```bash
python scripts/find_words.py --words private/words.txt              # 今のファイル
python scripts/find_words.py --words private/words.txt --history    # 履歴のすべての版と、コミットの作者・メッセージも
```
出力は場所と語の番号だけで、語そのものは出しません。ファイル冒頭の作者表記（「作成:」の行）は、作者が扱いを決めるまで数えません（`--include-author-lines` で数えます）。

## 期限の書き方
行の中に、丸括弧で期限を書きます。例: `資料作り (3/15まで)` → 題名「資料作り」・期限 3/15。

- 括弧は半角 `( )` でも全角 `（ ）` でもかまいません。数字と `/` も全角で読めます。
- 期限の部分は題名から除きます。期限と関係のない括弧（`(第2版)` など）は題名に残します。
- 1行は500文字まで、一度に解析できるのは200行までです。
- 読み方の正本は `backend/task_sync/date_rules.py` です。画面・API と、カレンダー同期用の `backend/task_sync/` が同じものを使います。
- 全部の例（154件）は共通検算表 `tests/fixtures/due_cases.json` にあります。

下の表の例は、今日が **2026-10-01（木）** のときです。

| 書き方 | 読み方 | 種類（due_type） | 例 |
|--------|--------|------|------|
| `(3/15まで)` `(3/15)` `(3月15日まで)` | その日。年は下の「年の決め方」 | exact | 2027-03-15 |
| `(2026/3/15)` `(2026年3月15日)` `(2026-03-15)` | 書いた年のその日 | exact | 2026-03-15（期限切れ） |
| `(令和8年12月1日)` `(R8.12.1)` | 和暦（令和・平成・昭和） | exact | 2026-12-01 |
| `(5日まで)` | 日だけ。今日以降なら今月、過ぎていれば翌月 | exact | 2026-10-05 |
| `(5月中)` `(5月まで)` `(5月末)` | その月の末日 | month_end | 2027-05-31 |
| `(月末)` `(今月中)` `(来月末)` | 今月・来月の末日 | month_end | 2026-10-31 |
| `(10月上旬)` `(中旬)` `(下旬)` | 上旬 = 10日、中旬 = 20日、下旬 = 末日。月が無ければ今月（過ぎていれば翌月） | period | 2026-10-10 |
| `(年内)` `(年度末)` | 12/31・3/31（4月始まりの年度） | month_end | 2027-03-31 |
| `(今週中)` `(来週まで)` `(来週)` `(再来週)` | その週の日曜日（週は月曜始まり） | week | 2026-10-11 |
| `(来週火曜)` `(今週金曜)` `(再来週月曜)` | その週のその曜日 | relative | 2026-10-06 |
| `(金曜まで)` | 次のその曜日（今日と同じ曜日なら今日・要確認） | relative | 2026-10-02 |
| `(今日中)` `(今夜)` `(明日)` `(明朝)` `(明後日)` `(3日後)` `(1週間以内)` | 今日から数えた日 | relative | 2026-10-02 |
| `(至急)` / `(大至急)` | 翌日 / 今日 | urgent | 2026-10-02 |
| `(早め)` `(なるはや)` `(なるべく早く)` `(ASAP)` | 3日後 | soon | 2026-10-04 |
| `(20日以降)` `(来週から)` `(11月から)` | この日以降（期間なら始まりの日。期限切れにはしない） | after | 2026-10-20 |
| 書かない | 期限なし | none | — |

### 時刻
- `15時` `午後3時` `10時半` `9:30` `正午` を読みます。API では `due_time`（HH:MM）で返し、`deadline` は日付の 0:00 のままです。
- 午前・午後の無い 1〜6時は午後（13〜18時）と読み、要確認にします。`24時` は 23:59 にします。
- `終日` と、数字の無い `午前中` `夕方` は時刻にしません。時刻だけ（`(17時まで)`）なら今日です。

### 年の決め方（年を書かない日付）
- 今日以降の日付は今年です。
- 過ぎた日付は、**62日前まで**なら今年のまま「期限切れ」にします（定数 `PAST_DUE_GRACE_DAYS`）。それより前なら翌年です。
  - 例（今日が 2026-10-01）: `(9/30まで)` → 2026-09-30 期限切れ。`(7/31まで)` → 2026-07-31 期限切れ（ちょうど62日前）。`(7/30まで)` → 2027-07-30。
- 翌年に繰り越す月末は、その年で数えます（翌年がうるう年なら 2/29）。
- 年の初めに去年の12月の日付を書くと、今年の12月になります。去年の分は年も書いてください。

### 週の数え方
- 週は**月曜始まり**です。「来週」は、次の月曜から始まる週です。
- **日曜に書いた「来週」**は、翌日の月曜からの週です。例: 2026-10-04（日）に書くと `(来週まで)` → 10/11、`(来週火曜)` → 10/6。
  日曜始まりで数える人とは1週間ずれるので、日曜に書いた「今週・来週・再来週・週末」には要確認の印を付けます。
- `(週末)` `(今週末)` は日曜にして、要確認にします（土曜とも読めるため）。

### 要確認（needs_review）になるもの
注意（warnings）が1つでもあれば要確認です。読めない行も捨てずに返します。
- 存在しない日付（`(2/30まで)`、平年の `(2/29まで)`、`(13/1まで)`）→ 期限なし。
- 期限らしいが読めない括弧（`(文化の日まで)` `(連休明け)` `(期限未定)`）→ 期限なし。括弧は題名に残します。
- 期限切れ（上の「年の決め方」、年つきの過去の日付、`(今週月曜)` など）。
- 日付が2つ以上（`(10/5か10/6)`、括弧が2つ）→ いちばん早い日。期間（`(10/5〜10/9)` `(10月5日から9日まで)`）→ 終わりの日。
- あいまいな言葉（頃・くらい・頭・毎週 など）、月だけ（`(10月)` → 月末）、日付と曜日の食い違い（`(11/3(月))`）。
- 括弧の外の期限らしい書き方（`明日までに〜`）。読みませんが、印を付けます。
- 期限だけの行（題名が無い）。

### 読まないもの（範囲）
- **祝日の判定はしません。** `(11/3まで)` はただの日付として読み、`(11/3(祝))` の「祝」も確かめません。祝日の名前（`(文化の日まで)`）は読まずに要確認にします。
- 外部の API やカレンダーは使いません（標準ライブラリだけで計算します）。
- `(10日分)` `(2/3ページ)` のような量は期限として読みません。ただし括弧の中の `(1/2)` は1月2日と読みます。

### API の応答
`/api/parse` と `/api/parse-batch` の各行は、`title`・`deadline`（JST の 0:00）・`category`・`raw_text`・`warnings` に加えて、
`due_type`（上の表の種類）・`due_raw`（読み取った括弧の中身）・`due_time`・`needs_review`・`overdue` を返します。
カテゴリについては `category_hits`（当たった語。空なら `default`）と `category_color`（印の色の番号 1〜6）も返します（上の「カテゴリの設定」）。
画面は「読み取り: 「3/15まで」→ 2027年3月15日（日付）」のように、どの表現をどう読んだかと、要確認・期限切れの印を出します。

## 画面の安全と見やすさ
- 画面の JS と CSS は `frontend/app.js`（ほかに `task_core.js`・`store.js`・`ics.js`）・`frontend/app.css` に分けています。HTML の中に script や style は書きません。
- 入力や API の応答の文字は `textContent` で表示します。`innerHTML` などで HTML として入れることはしません。
- すべての応答に、次のヘッダを付けます（`backend/api.py` の `SECURITY_HEADERS`）。
  - `Content-Security-Policy`: 自分のサーバーの JS・CSS だけを動かします（`script-src 'self'`）。ほかのサイトの枠（iframe）には入れさせません（`frame-ancestors 'none'`）。
  - `X-Content-Type-Options: nosniff`（宣言した種類以外として読ませない）・`Referrer-Policy: no-referrer`（ほかのサイトへ URL を渡さない）など。
  - `ENABLE_API_DOCS=1` のときの `/docs`・`/redoc` だけは CSP を付けません（外部の JS を使うため）。

### オフラインと新しい版（Service Worker）
- 画面（`/`・`index.html`・`app.js`・`task_core.js`・`store.js`・`ics.js`・`app.css`）は**ネット優先**です。つながらないときだけ、最後に取れた版（キャッシュ）を使います。
- 開けるものが何も無いときは、オフライン画面（`offline.html`）を出します。解析は電波のあるときだけできます。
- 新しい版が届くと、画面の上に「新しい版があります」と出ます。「更新する」を押すと切り替わります。
- **画面のファイルを変えたら**、`frontend/sw.js` の `CACHE_VERSION` を1つ上げて、`python scripts/sw_version.py --update` を実行します。
  上げ忘れはテスト（`tests/test_b28_service_worker.py`）で失敗になります。

### 見やすさ（アクセシビリティ）
- タブは矢印キー（← →）・Home・End で移れます。
- 「解析中…」・結果・エラーの知らせは、読み上げソフトに伝わる領域（aria-live）に出します。自動では消しません。
- 文字色と背景の対比は、すべて 4.5:1 以上です。色を変えたら `python scripts/contrast.py` で表を出して確かめます（テストでも確かめます）。
- ホーム画面のアイコンは、用途 any（そのまま）と maskable（丸などに切り抜かれる用）を分けています。maskable 用は `python scripts/make_maskable_icons.py` で作り直せます。

## 起動のしかた（手元）
Python 3.12 を想定しています（3.11 と 3.13 でもテストしています）。

```bash
python3 -m venv .venv
. .venv/bin/activate            # Windows（PowerShell）は .venv\Scripts\Activate.ps1
pip install -r requirements.txt
uvicorn backend.api:app --reload --port 8000
```

ブラウザで http://localhost:8000 を開くと画面が出ます。
API の説明ページ（`/docs`）は既定では出しません。手元で見たいときは `ENABLE_API_DOCS=1 uvicorn backend.api:app --port 8000` のように起動します（`.env.example` も参照）。
画面と API は同じサーバーから配信するので、他のサイトからの呼び出し（CORS）は許可していません。
`python main_api.py` でも同じアプリが起動します（同じ LAN のスマホからも開けます）。

## テストのしかた
```bash
pip install -r requirements.txt -r requirements-dev.txt
bash scripts/check.sh           # 構文確認 → ruff → pytest を1本で回す
```

画面の動きの試験（`tests/test_b28_frontend_js.py`・`tests/test_b29_frontend.py`）は node（18 以上）で `app.js`・`sw.js` を偽の DOM の上で動かします。
台帳の計算（`frontend/task_core.js`）は node の標準の `node:test` で検算します（`node --test tests/frontend/task_core.test.mjs`。pytest からも回ります）。node が無ければ飛ばします。

Windows（PowerShell）で bash が無いときは、同じことを次の1行で行います（venv を有効にしてから）。
`python -m compileall -q backend tests main_api.py; if ($?) { python -m ruff check . }; if ($?) { python -m pytest -q }`

GitHub では push と PR のたびに、同じ検証が Python 3.11 / 3.12 / 3.13 で自動で回ります（`.github/workflows/ci.yml`）。

## 依存ファイル
| ファイル | 用途 |
|----------|------|
| `requirements.txt` | 本番（Render）が読む、版を固定した依存。`requirements.in` から作る |
| `requirements-dev.txt` | テスト・lint 用（pytest・httpx2・ruff・icalendar） |
| `requirements-calendar.txt` | Google カレンダー連携の部品（`backend/task_sync/calendar_client.py`）用。画面と API には不要（Web アプリは使わない。上の「カレンダー用ファイル（.ics）」） |

依存を足すときは `.in` ファイルを直して、先頭に書いてあるコマンドで `.txt` を作り直します。
